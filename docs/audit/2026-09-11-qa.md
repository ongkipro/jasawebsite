# Repository, SEO, Performance, and Browser QA Audit

Date: 2026-09-11 (Asia/Jakarta). Repository: `ongkipro/jasawebsite`. Base: `96205ba46a890f70ce26e96070a1d37ea5b4adaa`. Branch: `audit/qa-seo-20260910`. Requirement: REQ-AUDIT-01; execution: TASK-44.

## Assessment and scope

The static site builds successfully and serves useful Indonesian service content, but its previous green checks and SEO score hid incorrect structured prices, unsupported structured claims, and interaction defects. This audit fixes the demonstrated issues locally and leaves measured performance and external evidence limits explicit. Nothing has been committed, pushed, or deployed.

Reviewed surfaces: all public content routes, metadata, schema, sitemap, robots, static assets, client/server boundaries, navigation/history, contact links, mobile/tablet/desktop layouts, modal/disclosure keyboard behavior, reduced motion, dependency audit, CI step outcomes, deployment evidence, and current project documentation.

- **Direct evidence:** source/diff inspection, generated HTML, 33 route exports, real local Chrome interactions, full Lighthouse JSON, public HTTP responses, npm audit, GitHub Actions step results.
- **Not established:** Google index coverage/rankings, field INP/CrUX, Search Console/Bing Webmaster ownership, conversion rates, portfolio business-metric provenance, Google Business Profile consistency, private deployment configuration.

- Preliminary local measurements from a minimal server without extensionless-route handling were excluded. The accepted local comparison uses the same loopback preview, gzip, full routing, Chrome, and Lighthouse profiles for both source revisions.

## SEO contract and page completeness

The site serves Indonesian buyers looking for a company profile, lead-generation landing page, online store/Shopify work, or a custom application. Main conversion intent is a contextual WhatsApp consultation. These are observed product/content intentions, not measured search demand.

| Intent / page type | URLs | Index/canonical policy | Content and internal linking |
| --- | --- | --- | --- |
| Broad commercial / studio entry | `/` | Index, canonical root | Introduction, services index, portfolio and contact links |
| Duplicate cover | `/folio/cover` | Retained 200 alias, canonical root, excluded from sitemap | Same cover experience; no competing canonical identity |
| Service selection | Company profile, sales, ecommerce/Shopify, custom app, maintenance | Self-canonical and indexable | Scope, tiers, starting prices, contextual WhatsApp |
| Trust / project evaluation | `/folio/portfolio` | Self-canonical and indexable | 13 portfolio entries and screenshots; business metrics require provenance |
| Industry discovery | `/folio/colophon` | Self-canonical and indexable | Search/filter, crawlable sector links, studio contact |
| Industry-specific commercial intent | 24 `/folio/niche-*` pages | Self-canonical and indexable | Industry problems, proposal/scope, starting price and contact |
| Missing content | Unknown URL | HTTP 404 and noindex | Recovery links and contact |

All exported pages are checked for canonical, title uniqueness (except the explicit cover alias), description, index directive, social card, initial semantic content, schema identity, actual WhatsApp destination, and existing local link targets. Browser checks cover one visible primary heading on initial views. CSS-hidden responsive copies remain in HTML; they are a documented rendering cost.

Title-length claims in earlier documents were too absolute: Google can truncate title links to fit device width and can choose alternate title text. Character counts do not guarantee an untruncated result. [Google title guidance](https://developers.google.com/search/docs/appearance/title-link).

Structured data describes visible, relevant content; syntax and a Lighthouse score alone cannot prove eligibility or truthfulness. [Google structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).

Sitemap URLs are canonical destinations. Modification dates are deliberately absent rather than generated from build time. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

## Security, code, and delivery review

The runtime has no authentication, database, payment endpoint, or inbound write API. Search/filter values stay in React-rendered local state; WhatsApp values are URL-encoded. No secrets, sessions, customer records, or private account data were accessed. npm audit reports no known vulnerabilities in the inspected dependency graph; this is not a penetration-test certification.

The two added tools, `lighthouse@13.4.1` and `puppeteer-core@25.10.0`, are pinned **development** dependencies. They provide reproducible performance/browser verification and do not enter the application bundle. Chrome is the existing system installation; no browser was downloaded. Preview binds loopback, restricts file resolution to the export directory, handles malformed URLs, and serves actual 404 status.

Public probes observed HTTPS 200 for the representative root/service/niche/robots/sitemap paths and 404 for a nonexistent path. Responses identify Vercel and include HSTS, nosniff, SAMEORIGIN, and a referrer policy. No SSL grade, edge region, global latency SLA, or multi-provider deployment is inferred from these headers.

The latest inspected [GitHub Actions run](https://github.com/ongkipro/jasawebsite/actions/runs/34504927238) passed its build checks but **skipped the Cloudflare deployment step**. CI success does not demonstrate a Cloudflare release. Existing action major-version references and manual deployment configuration remain operational follow-up items; no deployment workflow or infrastructure was changed.
